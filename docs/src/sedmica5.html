Imenovanje i komunikacija kao kod: DNS zone i zapisi u BIND-u (primarni i sekundarni server), zapisi kao Terraform resursi, e-pošta s Postfixom i Dovecotom uz TLS, SPF, DKIM i DMARC, te SFTP s chroot korisnicima iza vatrozida. Svaki servis se opisuje datotekama, a ishod se provjerava testom.

Ciljevi i način rada

U sedmici 4 je mreža odredila ko s kim smije razgovarati. Ova sedmica uvodi servise preko kojih ljudi i programi stvarno komuniciraju: DNS pretvara imena u adrese, e-pošta prenosi poruke između domena, a SFTP prenosi datoteke. Sva tri servisa su stari i dobro poznati, ali su i čest izvor problema: zaboravljen serial u DNS zoni, mail server koji prosljeđuje tuđu poštu (otvoreni relej) ili SFTP korisnik koji vidi cijeli disk servera. Kad je konfiguracija kod, takve greške se vide u pregledu promjene i hvataju testom.

Za rad nije potreban račun u oblaku ni domena. Svaki server radi u svom network namespace-u (kao u sedmici 4), na zajedničkom virtualnom switchu, a pravi programi (BIND, Postfix, Dovecot, OpenSSH) se pokreću s konfiguracijom iz repozitorija. Domena laba je ruo.lab i postoji samo u labu.

Nakon nastavne jedinice student je u stanju:

  • objasniti razliku između autoritativnog i rekurzivnog DNS servera, napisati zonsku datoteku i provjeriti je alatima named-checkconf i named-checkzone,
  • objasniti ulogu SOA seriala, NOTIFY poruke i prijenosa zone između primarnog i sekundarnog servera,
  • upravljati DNS zapisima kao Terraform resursima (RFC 2136, TSIG) i prepoznati drift,
  • postaviti mail server koji prima poštu za domenu, nije otvoreni relej, traži TLS i prijavu, i potpisuje poruke DKIM-om,
  • objasniti SPF, DKIM i DMARC i provjeriti ih na stvarnoj poruci,
  • generisati SFTP server s chroot korisnicima, ključevima i vatrozidom iz podataka (Ansible rola) i provjeriti idempotentnost.

Isti mehanizam se mogao koristiti za cijele direktorije (npr. /etc/postfix), ali primjeri radije zadaju putanju konfiguracije eksplicitno (named -c, postfix -c, dovecot -c, sshd -f), što radi i na pravom serveru.
2 · Pojam i pozadina

DNS: zone, zapisi i ko odgovara

DNS je distribuirana baza: niko nema cijelu bazu, nego je prostor imena podijeljen na zone, a za svaku zonu odgovaraju njeni autoritativni serveri. Korijen (.) zna ko odgovara za ba., ovaj zna ko odgovara za unze.ba., i tako dalje: to je delegacija, a ostvaruje se NS zapisima. Klijenti ne pitaju autoritativne servere direktno, nego rekurzivni resolver (onaj iz /etc/resolv.conf, npr. ruter, ISP ili 1.1.1.1) koji prolazi lancem delegacija i pamti odgovore onoliko dugo koliko kaže TTL.

Pozadina: primarni, sekundarni i serialZona se drži na najmanje dva servera, na različitim mrežama, jer bez DNS-a ne radi ništa drugo. Primarni ima izvor zone (datoteku ili bazu), a sekundarni drži kopiju koju preuzima prijenosom zone (AXFR cijela, IXFR samo razlike). Sekundarni preuzima zonu samo ako je serial u SOA zapisu veći od onog koji već ima. Nakon promjene primarni šalje NOTIFY, sekundarni uporedi serial i, ako je veći, povuče promjene; ako NOTIFY ne stigne, provjerava sam svakih refresh sekundi. Zaboravljen serial je zato klasična greška: primarni odgovara novim podacima, sekundarni starim, a klijent dobija jedan ili drugi odgovor zavisno od toga koga je pitao.

U oblaku se autoritativni DNS najčešće kupuje kao usluga (AWS Route 53, Azure DNS, Google Cloud DNS, Cloudflare): zona je resurs, a zapisi se mijenjaju kroz API. Na sopstvenim serverima se koriste BIND (najstariji i najpotpuniji), Knot i PowerDNS, a CoreDNS je DNS server od dodataka (plugin) koji je i zadani DNS u Kubernetesu (vidi napomenu u primjeru 1). Princip je svugdje isti: zona je kod ili podaci, a promjena prolazi provjeru prije objave.

3 · Primjer 1 · s5/p1

BIND: zona kao kod, primarni i sekundarni server

Pozadina primjeraZona ruo.lab je obična tekstualna datoteka u Gitu. Primarni server (ruo5-ns1) je učitava, a sekundarni (ruo5-ns2) nema vlastitih zonskih datoteka: sve preuzima od primarnog. Server je samo autoritativni (recursion no): odgovara za svoje zone, a tuđe domene odbija, što sprječava zloupotrebu servera za DNS amplifikacijske napade. Prijenos zone (AXFR) dozvoljen je samo sekundarnom, jer cijela zona otkriva sva imena i adrese u mreži.

named.confIsječak 2 · s5/p1/named-primarni.conf (izvod)
include "keys.conf";                  // TSIG ključevi: generišu se pri pokretanju, nisu u Gitu

options {
  listen-on { 10.50.0.53; 127.0.0.1; };
  recursion no;                       // samo autoritativni odgovori
  allow-transfer { 10.50.0.54; };     // kopiju cijele zone (AXFR) smije uzeti samo sekundarni
  notify yes;                         // nakon promjene javi sekundarnom (NOTIFY)
};

// statičke zone: datoteka je u Gitu, mijenja se commitom i povećanjem seriala
zone "ruo.lab"              { type primary; file "zone/db.ruo.lab"; };
zone "0.50.10.in-addr.arpa" { type primary; file "zone/db.10.50.0"; };

// dinamičke zone: zapise mijenjaju alati (RFC 2136), svaki ključ samo svoju zonu
zone "oblak.ruo.lab" {
  type primary; file "dyn/db.oblak.ruo.lab";
  update-policy { grant ruo-tf zonesub ANY; };          // Terraform (s5/p2)
};
zone "_domainkey.ruo.lab" {
  type primary; file "dyn/db._domainkey.ruo.lab";
  update-policy { grant ruo-dkim zonesub TXT; };        // DKIM ključ (s5/p3), samo TXT
};
Statičke i dinamičke zoneGlavna zona je statička: mijenja se samo kroz Git, pa svaka izmjena ima autora, opis i pregled. Zapise koje pravi automatika (Terraform, objava DKIM ključa, ACME izazovi) ima smisla odvojiti u posebne, delegirane zone koje se mijenjaju dinamičkim UPDATE-om. Tako glavna datoteka nikad ne dobije zapis koji nije prošao pregled, a svaki alat ima ključ koji smije mijenjati samo svoju zonu i samo potrebne tipove zapisa (načelo najmanjih prava, kao kod security grupa u sedmici 4).

DNS zapisi kao Terraform resursi

Pozadina primjeraProvider hashicorp/dns mijenja zapise standardnim protokolom za dinamičke izmjene (RFC 2136, DNS UPDATE), a svaki zahtjev potpisuje TSIG ključem (HMAC-SHA256 nad porukom i vremenom). Server iz primjera 1 prihvata UPDATE za zonu oblak.ruo.lab samo potpisan ključem ruo-tf. Tajna ključa se generiše pri pokretanju laba i nije u Gitu: make je predaje Terraformu kroz varijablu okruženja TF_VAR_tsig_secret, a varijabla je označena sensitive, pa se ne ispisuje u planu.
hclIsječak 4 · s5/p2/main.tf (izvod)
provider "dns" {
  update {
    server        = "10.50.0.53"
    key_name      = "ruo-tf."
    key_algorithm = "hmac-sha256"
    key_secret    = var.tsig_secret
  }
}

# servisi iz sedmice 4 (segmenti web/app/db) dobijaju imena; dvije adrese = dva A zapisa (round-robin)
variable "servisi" {
  type = map(list(string))
  default = {
    web = ["10.40.1.10", "10.40.1.11"]
    app = ["10.40.2.10"]
    db  = ["10.40.3.10"]
  }
}

resource "dns_a_record_set" "servis" {
  for_each  = var.servisi
  zone      = var.zona                      # "oblak.ruo.lab."
  name      = each.key
  addresses = each.value
  ttl       = 300
}

resource "dns_cname_record" "www" {
  zone  = var.zona
  name  = "www"
  cname = "web.${var.zona}"
  ttl   = 300
}

Granica: Terraform vidi samo svojeZapis koji neko doda ručno, a nije u kodu, Terraform ne primjećuje: state sadrži samo resurse koje je sam napravio. Zato se dinamičke zone daju samo jednom vlasniku (jedan ključ, jedan alat), a za potpunu kontrolu se zona periodično poredi s očekivanim stanjem (npr. dig AXFR i poređenje s izlazom terraform state list).

E-pošta: put poruke i tri provjere pošiljaoca

Poruka prolazi kroz više programa. Korisnik je predaje svom serveru preko submission porta (587, STARTTLS i obavezna prijava). MTA (Postfix) je prosljeđuje serveru primaoca, kojeg nalazi preko MX zapisa domene, na port 25. Server primaoca je predaje MDA-u (Dovecot, preko LMTP-a) koji je spremi u sanduče, a primalac je čita preko IMAP-a (143 sa STARTTLS ili 993 s TLS-om). U labu su pošiljalac i primalac na istom serveru, pa se korak "server na server" svodi na isporuku u lokalno sanduče.

SMTP je nastao kad su se svi serveri poznavali: polje From: može napisati bilo ko. Zato primalac danas provjerava pošiljaoca kroz tri mehanizma, a sva tri su DNS zapisi domene pošiljaoca, što ovu temu veže uz primjer 1:

SPFSmije li ova IP adresa slati poštu u ime domene (adresa iz envelope, MAIL FROM)?ruo.lab TXT "v=spf1 mx -all": samo MX serveri; -all = sve ostalo odbij
DKIMDa li je poruku potpisala domena i da li je neizmijenjena?ruo2026._domainkey.ruo.lab TXT "v=DKIM1; k=rsa; p=MIIB...": javni ključ
DMARCPoklapa li se domena iz SPF-a ili DKIM-a s domenom iz From: (poravnanje), i šta raditi ako ne?_dmarc.ruo.lab TXT "v=DMARC1; p=reject; adkim=s; aspf=s; rua=..."
Pozadina: zašto treba i DMARCSPF i DKIM sami ne štite polje From: koje korisnik vidi. Napadač može proći SPF za svoju domenu (MAIL FROM: x@napadac.com) i potpisati poruku svojim DKIM ključem (d=napadac.com), a u From: napisati direktor@ruo.lab. DMARC traži da bar jedna od dvije provjere prođe za istu domenu koja je u From:. Politika p=reject kaže primaocu da takvu poruku odbije, a rua je adresa na koju primaoci šalju zbirne izvještaje. U praksi se kreće od p=none (samo izvještaji), pa kad izvještaji pokažu da sva legitimna pošta prolazi, prelazi na quarantine i reject. Od 2024. godine Gmail i Yahoo za masovne pošiljaoce traže sve tri provjere.
TLS i ACMECertifikat u labu izdaje lokalni CA (mail.sh ga pravi naredbom openssl), a klijenti ga provjeravaju jer im je CA eksplicitno zadan. Na javnom serveru certifikat izdaje javni CA protokolom ACME (Let's Encrypt, certbot), koji prvo provjeri da podnosilac kontroliše domenu: HTTP-01 (datoteka na web serveru) ili DNS-01 (TXT zapis _acme-challenge). DNS-01 je jedini način za wildcard certifikat i za servere bez web servera, kakav je mail server. Dodatak certbot-dns-rfc2136 taj TXT zapis upisuje istim mehanizmom kao Terraform u primjeru 2: dinamičkim UPDATE-om s TSIG ključem, idealno u posebnu, delegiranu zonu _acme-challenge. Zapis CAA u zoni pri tome ograničava koji CA uopće smije izdati certifikat.

SFTP s chroot korisnicima iz podataka: Ansible rola

Pozadina primjeraSFTP je protokol za prijenos datoteka unutar SSH veze: šifrovan je, koristi SSH ključeve i ne treba posebne portove, za razliku od starog FTP-a (nešifrovane lozinke, odvojena podatkovna veza) i FTPS-a. Za korisnike koji samo razmjenjuju datoteke (partneri, skripte za backup) važno je ograničiti ih: ForceCommand internal-sftp ne dozvoljava shell, a ChrootDirectory korijen sesije pretvara u jedan direktorij, pa korisnik ne vidi ostatak diska. Chroot ima strogo pravilo: direktorij i svi roditelji moraju pripadati root-u i niko drugi ne smije pisati u njih, inače sshd odbija prijavu. Zato korisnik dobija poddirektorij upload u koji jedino smije pisati.

Rola koristi isti obrazac kao vatrozid iz sedmice 4: politika je u podacima, a šabloni od nje prave konfiguraciju. Novi korisnik je jedan red u vars.yml:

PitanjeOdgovor
Koja je razlika između autoritativnog i rekurzivnog DNS servera?Autoritativni je izvor podataka za svoje zone; rekurzivni za klijenta prolazi lanac delegacija od korijena i pamti odgovore koliko kaže TTL.
Zašto sekundarni nije preuzeo izmjenu zone?Serial u SOA zapisu nije povećan; sekundarni preuzima zonu samo kad je serial veći od njegovog.
Šta je glue zapis i kada je potreban?A zapis za ime NS servera unutar zone koju taj server poslužuje; bez njega resolver ne bi mogao doći do servera.
Zašto server za example.com vraća REFUSED?Server je samo autoritativni (recursion no) i ne odgovara za tuđe zone; otvoreni rekurzivni server se zloupotrebljava za DDoS.
Čemu služi TSIG ključ u primjeru 2?Potpisuje DNS UPDATE, pa server prihvata izmjene samo od vlasnika ključa, i to samo u zoni koju mu dozvoljava update-policy.
Šta je otvoreni relej i koje pravilo ga sprječava?Server koji prosljeđuje poštu bilo koga bilo kome; reject_unauth_destination dozvoljava tuđe domene samo prijavljenim korisnicima.
Šta provjerava SPF, a šta DKIM?SPF: smije li IP adresa slati za domenu iz envelope pošiljaoca. DKIM: potpis domene nad zaglavljima i tijelom, pa i neizmijenjenost poruke.
Zašto treba DMARC ako postoje SPF i DKIM?Tek DMARC traži da domena iz SPF-a ili DKIM-a odgovara domeni iz From: koju korisnik vidi, i kaže primaocu šta da uradi ako ne odgovara.
Zašto chroot direktorij mora pripadati root-u?Inače bi korisnik u korijen mogao postaviti datoteke (npr. lažni /etc) i zloupotrijebiti programe koji se izvršavaju s višim pravima; sshd takvu konfiguraciju odbija.
Zašto su javni ključevi korisnika u direktoriju koji pripada root-u?Korisnik ne može sam dodati ključ; spisak dozvoljenih ključeva je uvijek onaj iz koda.
