Ciljevi i način rada

U prethodne tri sedmice su mašine i servisi opisani kodom. Ostaje pitanje ko s kim smije razgovarati. Mreža i vatrozid su najčešći izvor grešaka i sigurnosnih propusta, a ručno podešavanje je teško ponoviti i još teže pregledati. Zato se i oni pišu kao kod: pravila su u datoteci, datoteka je u Gitu, a ishod se provjerava testom, ne pogađanjem.

Za rad nije potreban račun u oblaku. Mrežni elementi (ruter, segmenti) prave se od Linux network namespace-ova, istog mehanizma na kojem se zasnivaju kontejneri iz prve sedmice. Jedan namespace je jedna izolirana mreža sa svojim sučeljima, adresama i tabelom usmjeravanja, pa tako radi i svaka mašina u labu.

Nakon nastavne jedinice student je u stanju:

  • povezati pojmove oblaka (VPC, subnet, route table, NAT, security group) s Linux alatima koji ih ostvaruju,
  • napraviti segmentiranu mrežu s ruterom i NAT-om i objasniti put paketa kroz nju,
  • napisati stateful vatrozid s politikom "sve zabranjeno, dozvole se nabrajaju" u nftables i provjeriti ga matricom povezivosti,
  • generisati pravila vatrozida iz podataka Ansible rolom i provjeriti idempotentnost,
  • objasniti razliku između L2 (bridge, VLAN) i L3 (ruter) segmentacije.

Od mašina do mreže

Mreža u oblaku se sastoji od nekoliko elemenata koje svaki pružatelj (AWS, Azure, GCP) naziva drugačije, ali rade isto. Na Linuxu svaki od njih ima konkretnu zamjenu, pa se isto razmišljanje može vježbati lokalno i besplatno.

Pozadina: nftablesLinux vatrozid je dugo bio iptables (više odvojenih alata za IPv4, IPv6, ARP). nftables ga je zamijenio 2014. godine (jezgra 3.13): jedan alat, jedan jezik, skupovi (sets) i atomsko učitavanje cijele datoteke, a od Debiana 10 je i zadani. Pravila su organizovana u tabele (table), tabele u lance (chain), a lanci se vežu na hook u putu paketa kroz jezgru: input (paket za sam ruter), forward (paket koji prolazi kroz ruter), output i prerouting/postrouting (NAT). Praćenje veza (connection tracking, ct) pamti stanje, pa vatrozid dozvoljava odgovore na dozvoljene veze bez posebnog pravila.
Zašto segmentacijaAko napadač preuzme web server, u ravnoj mreži odmah vidi i bazu. Segmentacijom je web smije dosegnuti samo kroz aplikacijski port, a bazu uopće ne. Politika "sve zabranjeno, dozvole se nabrajaju" (default deny) znači da zaboravljeno pravilo uzrokuje prekid veze koji se odmah primijeti, a ne tihu rupu.
2 · Primjer 1 · s4/p1

Segmenti, ruter i NAT od namespace-ova

Pozadina primjeraSvaki segment je namespace (ruo-web, ruo-app, ruo-db) spojen na ruter ruo-rtr veth parom: virtualnim kablom čiji se jedan kraj nalazi u segmentu, a drugi u ruteru. Ruter ima po jedno sučelje u svakom segmentu (.1 u podmreži) i uplink prema "internetu" (host). Mašine u segmentu imaju zadani put (default via) preko rutera. Bez net.ipv4.ip_forward=1 ruter ne bi prosljeđivao pakete, što je čest razlog zašto "sve je spojeno, a ništa ne radi".
bashIsječak 1 · s4/p1/lab.sh (izvod)
  # 1. ruter i uplink prema "internetu" (host)
  run ip netns add ruo-rtr
  run ip link add h-up type veth peer name r-up netns ruo-rtr
  run ip addr add 10.40.0.1/30 dev h-up
  run ip link set h-up up
  run ip -n ruo-rtr addr add 10.40.0.2/30 dev r-up
  run ip -n ruo-rtr link set lo up
  run ip -n ruo-rtr link set r-up up
  run ip route add 10.40.0.0/16 via 10.40.0.2          # povratni put do segmenata
  rtr sysctl -qw net.ipv4.ip_forward=1                 # ruter prosljeđuje pakete
  run ip -n ruo-rtr route add default via 10.40.0.1

  # 2. segmenti: namespace + veth par prema ruteru + zadani put preko rutera
  for s in $SEGMENTI; do
    ime="${s%%:*}"; n="${s##*:}"
    run ip netns add "ruo-$ime"
    run ip link add "r-$ime" netns ruo-rtr type veth peer name eth0 netns "ruo-$ime"
    run ip -n ruo-rtr addr add "10.40.$n.1/24" dev "r-$ime"
    run ip -n ruo-rtr link set "r-$ime" up
    run ip -n "ruo-$ime" addr add "10.40.$n.2/24" dev eth0
    run ip -n "ruo-$ime" link set lo up
    run ip -n "ruo-$ime" link set eth0 up
    run ip -n "ruo-$ime" route add default via "10.40.$n.1"
  done

Ruter ima put do svake podmreže jer su mu sučelja direktno u njima (proto kernel scope link), a sve ostalo ide na default via 10.40.0.1. Isti princip vrijedi u oblaku: odgovor mora imati put nazad, a u tabeli usmjeravanja je to route table podmreže.

NATPrivatne adrese (10.0.0.0/8) se ne usmjeravaju po internetu. Masquerade mijenja izvornu adresu paketa u adresu izlaznog sučelja rutera i pamti prevod, pa se odgovor vraća pravoj mašini. To je SNAT kakav radi kućni ruter i NAT gateway u oblaku. Pravilo je u lancu postrouting (Isječak 3).

Vatrozid u nftables: default deny i segmentacija

Pozadina primjeraPravila se učitavaju u ruter, pa vrijede za sav promet između segmenata. Lanac forward ima policy drop: sve što nijedno pravilo ne dozvoljava pada. Prvo pravilo (ct state established,related accept) propušta odgovore na dozvoljene veze, pa je dovoljno opisati samo smjer uspostave veze (stateful vatrozid, kao security group u oblaku). Datoteka počinje s table inet ruo i delete table inet ruo: prvi red osigurava da tabela postoji (inače bi brisanje javilo grešku), a drugi je briše, pa učitavanje uvijek počinje od čistog stanja i može se ponavljati (idempotentnost). Cijela datoteka se učitava atomski: ili sva pravila, ili nijedno.
nftIsječak 3 · s4/p2/firewall.nft
#!/usr/sbin/nft -f
# s4/p2: segmentacija web/app/db na ruteru (ruo-rtr). Učitava se atomski: cijela datoteka ili ništa.
# Idiom "table ...; delete table ...; table ... { }" čini učitavanje idempotentnim bez diranja tuđih tabela.

define web    = 10.40.1.0/24
define app    = 10.40.2.0/24
define db     = 10.40.3.0/24
define uplink = "r-up"

table inet ruo
delete table inet ruo

table inet ruo {
  set web_ports { type inet_service; elements = { 80, 443 } }

  # promet KROZ ruter (između segmenata): zadano je zabrana, dozvole se nabrajaju
  chain forward {
    type filter hook forward priority filter; policy drop;

    ct state established,related accept          # odgovori na dozvoljene veze
    ct state invalid drop

    iifname $uplink ip daddr $web tcp dport @web_ports accept   # internet -> web: samo 80/443
    ip saddr $web ip daddr $app tcp dport 8080 accept           # web -> app: samo aplikacijski port
    ip saddr $app ip daddr $db  tcp dport 5432 accept           # app -> db: samo baza
    ip saddr { $web, $app } oifname $uplink accept              # izlaz prema internetu: web i app, ne db

    limit rate 5/minute log prefix "ruo-drop: "                 # sve ostalo pada (policy drop)
  }

  # promet KA samom ruteru
  chain input {
    type filter hook input priority filter; policy drop;
    iifname "lo" accept
    ct state established,related accept
    icmp type echo-request limit rate 5/second accept
  }

  # NAT: segmenti izlaze prema uplinku s adresom rutera
  chain postrouting {
    type nat hook postrouting priority srcnat;
    oifname $uplink ip saddr 10.40.0.0/16 counter masquerade
  }
}

nftIsječak 5 · nft list chain inet ruo forward (stanje u jezgri)
table inet ruo {
  chain forward {
    type filter hook forward priority filter; policy drop;
    ct state established,related accept
    ct state invalid drop
    iifname "r-up" ip daddr 10.40.1.0/24 tcp dport @web_ports accept
    ip saddr 10.40.1.0/24 ip daddr 10.40.2.0/24 tcp dport 8080 accept
    ip saddr 10.40.2.0/24 ip daddr 10.40.3.0/24 tcp dport 5432 accept
    ip saddr { 10.40.1.0-10.40.2.255 } oifname "r-up" accept
    limit rate 5/minute burst 5 packets log prefix "ruo-drop: "
  }
}
Šta jezgra radi s pravilimaIspis stanja se razlikuje od izvorne datoteke: @web_ports ostaje skup, a lista { $web, $app } je spojena u interval 10.40.1.0-10.40.2.255 jer su podmreže susjedne. Smisao je isti, ali treba znati čitati ispis. Brojači (counter) se mogu dodati pravilima da se vidi koliko je paketa pogodilo koje pravilo, što je prvi alat za otkrivanje zašto veza ne radi.

Bridge i VLAN: segmentacija na sloju 2

Pozadina primjeraDo sada je segmentacija bila na sloju 3: ruter razdvaja podmreže, a vatrozid odlučuje šta prolazi. Bridge je virtualni preklopnik (sloj 2): prosljeđuje okvire između portova prema MAC adresama. VLAN (IEEE 802.1Q) dijeli taj preklopnik na više odvojenih L2 domena. Okvir nosi oznaku s brojem VLAN-a (od 1 do 4094), a preklopnik ga isporučuje samo portovima istog VLAN-a. Na pristupnom (access) portu mašina ne vidi oznake: preklopnik sam stavlja njene okvire u zadani VLAN (pvid). Zato dvije mašine u različitim VLAN-ovima ne mogu razgovarati čak ni kad su im adrese u istoj podmreži.
bashIsječak 6 · s4/p3/vlan.sh (izvod)
port() { # ime  vlan  ip     pristupni port: okviri bez oznake ulaze u zadani VLAN
  run ip netns add "ruo-$1"
  run ip link add "p-$1" netns ruo-sw type veth peer name eth0 netns "ruo-$1"
  run ip -n ruo-sw link set "p-$1" master br0
  run ip -n ruo-sw link set "p-$1" up
  run bridge -n ruo-sw vlan add dev "p-$1" vid "$2" pvid untagged   # ulazni okvir bez oznake -> VLAN $2
  run bridge -n ruo-sw vlan del dev "p-$1" vid 1                    # ukloni zadani VLAN 1 s porta
  run ip -n "ruo-$1" addr add "$3" dev eth0
  run ip -n "ruo-$1" link set lo up
  run ip -n "ruo-$1" link set eth0 up
}

gore() {
  run ip netns add ruo-sw
  run ip -n ruo-sw link add br0 type bridge vlan_filtering 1   # bez vlan_filtering bridge ignoriše VLAN-ove
  run ip -n ruo-sw link set br0 up
  port h10a 10 10.50.10.11/24
  port h10b 10 10.50.10.12/24
  port h20  20 10.50.10.21/24     # ista podmreža, ali drugi VLAN: izolirana je na sloju 2
}

Vatrozid iz podataka: Ansible rola

Pozadina primjeraRučno pisanje pravila ne skalira: nova usluga znači izmjenu više redova na više mjesta. Ovdje se politika opisuje podacima (koji segment smije kojem, na kojem portu), a šablon ih pretvara u nftables. Tako se pravila pregledaju kao podaci, a generisanje je jedno mjesto koje se testira. Rola koristi alate iz sedmice 3: šablon (Jinja2), handler i validate, kojim se izgenerisana datoteka provjerava prije nego što zamijeni radnu.
yamlIsječak 8 · s4/p4/group_vars/rtr/vars.yml
# Politika mreže kao PODACI: pravila se mijenjaju ovdje, a šablon ih pretvara u nftables.
fw_uplink: r-up

fw_segmenti:                     # ime: podmreža
  web: 10.40.1.0/24
  app: 10.40.2.0/24
  db: 10.40.3.0/24

fw_javno:                        # internet -> segment
  - { do: web, portovi: [80, 443] }

fw_pravila:                      # segment -> segment (slojevi: web -> app -> db)
  - { od: web, do: app, portovi: [8080] }
  - { od: app, do: db,  portovi: [5432] }

fw_izlaz: [web, app]             # segmenti kojima je dozvoljen izlaz prema internetu (db nije)

# U labu se pravila učitavaju u namespace rutera iz s4/p1; na pravom ruteru ostaje samo "nft".
fw_nft_cmd: ip netns exec ruo-rtr nft
fw_dest: /etc/nftables.d/ruo.nft
fw_instaliraj_paket: true

PitanjeOdgovor
Zašto ruter bez ip_forward=1 ne prosljeđuje pakete?Jezgra zadano odbacuje pakete koji nisu za nju; prosljeđivanje se mora uključiti, čime je ruter svjesna odluka, a ne nuspojava.
Čemu služi ct state established,related accept?Propušta odgovore na već dozvoljene veze, pa se pravilima opisuje samo smjer uspostave veze.
Zašto datoteka počinje s table pa delete table?Učitavanje počinje od čistog stanja i ne javlja grešku ako tabela ne postoji, pa je idempotentno.
Zašto jedna tabela s accept ne otvara ono što druga zabranjuje?Paket mora proći sve lance na istom hooku; accept završava samo svoj lanac.
Po čemu se VLAN razlikuje od podmreže?VLAN je L2 domena (ko dijeli okvire), podmreža je L3 adresni opseg; obično su 1:1, ali nisu isto. U Primjeru 3 su dvije mašine u istoj podmreži, ali u različitim VLAN-ovima, pa ne mogu razgovarati.
Čemu validate u zadatku template?Neispravna datoteka se provjeri prije zamjene radne, pa greška u šablonu ne ruši vatrozid.

Zadaci za samostalni rad

  1. U firewall.nft dodati pravilo koje dozvoljava web prema app na port 9090, učitati ga i u test.sh dodati dvije provjere (dozvoljeno 9090, blokirano 9091). Objasniti zašto bez pravila veza ne radi.
  2. Privremeno ukloniti ct state established,related accept i pokrenuti test. Objasniti šta se desi s odgovorima i zašto se pravilo vraća.
  3. U vars.yml dodati segment cache (10.40.4.0/24) i pravilo app → cache na port 6379 te segment dodati u SEGMENTI u lab.sh. Pokrenuti rolu dva puta i predati izlaz drugog izvršavanja.
  4. Svakom pravilu u lancu forward dodati counter, pokrenuti test i objasniti koji brojač je porastao pri kojoj provjeri.
  5. U vlan.sh dodati treći VLAN (30) s jednom mašinom i proširiti test izolacije (zahtijeva jezgru s VLAN podrškom).
